*2026年10月22日現在｜世界中で対応継続中*

現在、インターネットの安全性を根本から揺るがす重大なセキュリティ問題への対応が、世界中で進められています。

**私たちが普段使っているPCやスマートフォン、さまざまなアプリも無関係ではありません。**

## 何が起きているの？

Webサイトやアプリは、通信相手が本物であることを「電子証明書」という仕組みで確認しています。

ところが今回、その証明書を発行する企業「eMudhra（イームドラ）」で、**悪意のある第三者でも本物と区別がつかない証明書を偽造できてしまう重大な欠陥**が発覚しました。

例えるなら、世界中で信用されている身分証明書の発行機関で、誰でも本物そっくりの身分証明書を作れる状態になっていたようなものです。

しかも、これはWebブラウザだけの問題ではありません。

SNS、メール、チャット、ネットバンキング、会社の業務システムなど、**インターネットで通信するあらゆるアプリが、対策状況を確認すべき対象**です。

普段どおりに動いているアプリでも、安全だとは限りません。

## 放置すると、どれくらい危険？

対策されていない環境で悪用された場合、最悪、次のような被害につながる恐れがあります。

- **銀行口座の情報を盗まれ、不正送金される**
- **SNSやメール、業務アカウントを乗っ取られる**
- **通信内容を盗み見られたり、書き換えられたりする**
- **正規のソフトウェアを装ったウイルスに感染する**
- **会社の機密情報や顧客情報が流出する**
- **企業全体の業務停止や巨額の損害につながる**

これらは、攻撃者が通信を偽装するなどの条件がそろった場合に想定される被害です。現時点で、今回の問題による大規模な悪用が確認されたわけではありません。

## 今すぐ何をすればいい？

ChromeやFirefoxなどの主要ブラウザでは緊急対策が行われています。しかし、**ブラウザが安全でも、他のアプリやシステムまで安全になるとは限りません。**

以下の対応を徹底してください。

1. **PC・スマートフォンのOSと、普段使っているアプリを最新の状態にする。** 更新後は端末を再起動してください。
2. **更新できない古い端末やアプリは注意する。** 安全性が確認できない場合は、重要な情報の取り扱いを避け、管理者に相談してください。
3. **セキュリティ警告を絶対に無視しない。** 接続エラーや証明書の警告を無理に突破しないでください。
4. **業務システムの管理者は、アプリやサーバー側の対策も確認する。** OSやブラウザの更新だけでは不十分な場合があります。

## 自分の環境は大丈夫？ 無料チェックツール

今回の問題について、使用中のブラウザが危険な証明書を受け入れてしまうか確認できるツールが公開されています。

**[eMudhra セキュリティチェックツールを開く](https://emudhra.we-have-a-problem.com/#check)**

使い方は簡単です。

1. 上記のサイトにアクセスし、「Run check」を押す。
2. 緑色の「Did not connect」が表示されれば、その項目では問題のある接続が成立していません。
3. 赤色の「Connected」が表示された場合は要注意。問題の証明書を使った接続が成立しているため、更新と再確認が必要です。

このツールは、Mozillaのセキュリティ担当者が公開しているオープンソースの検証サイトです。

ただし、**このチェックで問題がなくても、PCやスマートフォンに入っているすべてのアプリが安全という意味ではありません。** また、通信のタイムアウトなどによって接続できなかった場合は、必ずしも安全性を確認できたとは限りません。

現在も各社による対策が続いています。

**「いつものアプリだから大丈夫」「今まで問題なかったから安全」という思い込みは禁物です。**

自分自身と会社の情報を守るため、今すぐソフトウェアの更新状況を確認しましょう。

## 詳しい人向け：技術的な背景と対策

ここからは、今回のインシデントの技術的な原因と影響、ソフトウェア開発者・システム管理者が取るべき対応を解説します。

### 1. 何が侵害されたのか

2026年10月17日、eMudhraが2025年4月30日に生成した8つの中間認証局（Intermediate CA）の秘密鍵が、公開情報から極めて容易に復元できることが報告されました。

内訳は以下のとおりです。

- TLS証明書用の中間CA：6件
- コード署名用の中間CA：2件

問題の鍵は楕円曲線暗号のP-384鍵で、本来は十分な乱数から生成されるべき秘密鍵が、すべて256未満の整数になっていました。

つまり、本来は極めて広大な鍵空間を持つはずが、わずか255通りを調べるだけで秘密鍵を特定できる状態だったのです。

Mozillaは第三者からの報告後、独立に鍵を復元して問題を確認しています。

eMudhraの調査によると、鍵生成時のスクリプトに不備があり、想定外に生成された弱い鍵が、正規の鍵と取り違えられて証明書に使用されたとされています。

**暗号方式そのものが破られたのではなく、鍵生成と管理のプロセスに重大な欠陥が存在した**という問題です。

なお、eMudhraはルートCAの秘密鍵自体は侵害されていないと説明しています。

### 2. どのような攻撃が成立するのか

攻撃者が問題の中間CAの秘密鍵を使用すると、任意のドメインに対するTLS証明書を偽造できます。

そのため、問題の中間CAを信頼し続けているクライアントでは、DNS改ざんや通信経路の乗っ取りなどと組み合わせることで、TLS通信の中間者攻撃（MITM）が成立する恐れがあります。

攻撃者が行える可能性があるのは、接続先のなりすまし、通信の盗聴・改ざんなどです。

また、影響を受けた中間CAにはコード署名用のものも含まれるため、署名検証の条件によっては、不正なソフトウェアを正規の発行元が署名したものと誤認させるリスクもあります。

#### Certificate Transparencyによる保護

Chromeなどの主要ブラウザは、公開証明書の発行履歴を確認するCertificate Transparency（CT）を採用しています。

今回、問題の中間CAが発行したTLS証明書は、遮断措置が行われる前のCTログには登録されていませんでした。

そのため、CTを必須としているChromeなどの通常環境では、問題発覚以前から偽造証明書を受け入れない状態だったと考えられています。

しかし、**CTを検証しないアプリケーションやサーバー間通信では、この保護が働きません。**

これが、ブラウザで緊急対応が進んだ後も問題が残る大きな理由です。

### 3. なぜブラウザ以外にも影響するのか

電子証明書の検証方法は、アプリケーションによって異なります。

例えば、OSが管理する証明書を使うものもあれば、独自の証明書一覧を内蔵するもの、開発言語や実行環境が提供する仕組みを使うものもあります。

具体的には、次のようなソフトウェアが個別の影響確認を必要とします。

| 分類 | 主な例 |
|---|---|
| デスクトップアプリ | Electron製アプリなど |
| アプリの実行環境 | Node.js、Go、Java、Python |
| 通信・証明書検証 | OpenSSL、curl、NSS、certifi、rustls |
| サーバー・インフラ | APIサーバー、コンテナ、プロキシ、VPN |
| モバイルアプリ | 独自の通信処理や証明書検証を行うアプリ |

特にElectronは、Slack、Discord、VS Codeなど、多数のデスクトップアプリに採用されています。

Electron自体に修正が入っても、それを利用する個々のアプリが修正版へ更新されなければ、必要な対策が反映されない場合があります。

また、macOSではOS側で問題の証明書が遮断されていても、標準のcurl、git、Pythonなどが参照する証明書ファイルには対策が反映されていないケースが報告されています。

**OSの更新状況だけで、すべての通信処理の安全性を判断することはできません。**

### 4. 各社の対応状況

2026年10月22日時点で、主に以下の対応が確認されています。

- **Chrome：** 10月17日にCRLSetを更新し、問題の中間CAの公開鍵を遮断。
- **Firefox：** 同日にOneCRLを更新。Firefox 158.0.1などにも対策を収録。
- **Apple：** 10月19日までに関連証明書の遮断措置を実施。
- **Microsoft：** 10月20日までに関連する信頼情報の更新を実施。
- **Android：** Google Play開発者サービスを通じて追加の保護情報を配信。
- **その他：** 各OS・実行環境・証明書管理パッケージで修正版の公開が進行中。

例えば、修正版としてGo 1.26.10 / 1.27.3、NSS 3.131.1、Python certifi 2026.10.19、Electron 42.11.16 / 43.8.1 / 44.9.1などが公開されています。

さらにGoogleは、10月27日（米国太平洋時間）に「emSign ECC Root CA - G3」をChromeの信頼対象から外す予定です。

これにより、同ルートに依存する正常なWebサイトでも、証明書の切り替えが完了していなければ接続障害が発生する可能性があります。

### 5. 開発者・システム管理者が実施すべきこと

今回の問題では、単純なOSアップデートだけでなく、**実際に通信を検証しているコンポーネントまで確認すること**が重要です。

- 証明書の信頼情報と失効情報が最新か確認する。
- 使用している言語ランタイム、通信ライブラリ、Electronなどを更新する。
- コンテナやサーバーイメージを更新・再ビルドし、必要に応じて再デプロイする。
- 独自の証明書ストアや証明書検証処理がないか確認する。
- 重要な外部API接続について、実際の通信経路で検証する。
- 証明書エラーが発生しても、検証処理を無効化して回避しない。

#### コマンドラインでの検証

前述のチェックサイトには、curlなどから検証するためのテスト用接続先も用意されています。

```bash
curl https://dv-g3b-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-emudhra.we-have-a-problem.com/
```

これらは、問題の中間CAにつながる証明書を使ったテストサイトです。

- **証明書の検証エラー：** その接続経路では問題の証明書が拒否されている。
- **接続成功：** その接続経路が問題の証明書を受け入れているため、対応が必要。
- **タイムアウト等：** ネットワークの問題でも発生するため、結果だけでは判断できない。

ただし、curlでの検証結果も、別の通信機構を使うアプリの安全性までは保証しません。

WindowsなどのOS証明書ストアを使う場合と、独自の証明書バンドルを使う場合では、結果が異なることがあります。

そのため、重要な業務システムについては、**対象アプリケーション自身が使用するTLS検証処理で確認する必要があります。**

検証用サイトには各OS向けの対策方法も掲載されていますが、証明書ストアを直接変更する操作は、他の正常な通信にも影響する場合があります。管理端末や本番環境では、変更内容を検証したうえで実施してください。
