## はじめに

WebAssemblyにコンパイルできる静的型付き言語「Restrict」を作っています。
先日、最初の公開バージョンv0.0.1をリリースしました。

Restrictの特徴は、関数の前に値を置くOSV（Object–Subject–Verb）語順です。
ただし、変わった構文を試すためだけの言語ではありません。

値がどこへ渡り、どこで使えなくなるか。
どのスコープで何を参照できるか。
誰が値を所有するか。
この3つを、ソースコードの順序と型で表すことを目指しています。
その設計を、WebAssemblyまでコンパイルできる処理系として実装しました。

この記事では、リリース内容を網羅しません。
Restrictがどのような考えで作られているのかを、日本語で紹介します。
現在の実装範囲をまとめた公式記事は、英語で公式サイトに掲載しています。

## OSV語順とは

Restrictの通常の関数呼び出しは、値を先に、関数を後に書きます。
直接呼び出す場合もパイプを使う場合も、値から処理へ向かう順序は同じです。
Restrictでは、この規則をOSV語順と呼んでいます。

一般的な関数呼び出しでは、最初に関数名を書き、その後ろの括弧に引数を置きます。

```text
increment(20)
add(10, 20)
```

Restrictでは、通常の関数呼び出しをOSV語順に統一しています。

```text
20 increment
(10, 20) add
```

引数の値が先に来て、最後に処理を表す関数を置きます。
引数が1つの場合は、パイプも使えます。

```text
fun increment: (value: Int32) -> Int32 = {
    value + 1
}

fun double: (value: Int32) -> Int32 = {
    value * 2
}

fun main: () -> Int32 = {
    20
        |> increment
        |> double
}
```

この例は「20をincrementし、その結果をdoubleする」と、処理される値から順番に読めます。

`20 increment`と`20 |> increment`は、同じ呼び出し規則に従っています。
パイプは、通常の関数呼び出しとは別に追加した省略記法ではありません。
Restrictは、`increment(20)`のように関数を先に書く呼び出しを受け付けません。

構文を1種類に絞りました。
これにより、関数・メソッド相当の処理・列挙型のコンストラクタ・処理の連鎖を、すべて同じ順序で読めます。

名称はObject–Subject–Verbに由来しますが、自然言語の語順をそのままプログラミング言語に持ち込んだものではありません。
宣言や二項演算を含むすべての構文が、厳密なOSVになるわけでもありません。
Restrictでは、関数呼び出しを中心とした式の並び方を説明する設計用語として使っています。

## まずはブラウザで動かす

RestrictのPlaygroundでは、コードをブラウザ内でコンパイルして実行できます。
次のプログラムは文字列を標準出力に表示します。

```text
fun main: () -> () = {
    "Hello, Restrict!" |> println
}
```

`"Hello, Restrict!"`が先にあり、それを受け取る`println`が後ろにあります。
`|>`を使うと、値が左から右へ流れます。

Playgroundは、用意した例だけを動かすデモではありません。
ブラウザ向けにビルドしたコンパイラが、入力を字句解析・構文解析・型検査し、WebAssemblyを生成して実行します。
画面上では、プログラムの出力に加えて、トークン・AST・生成されたWebAssembly・コンパイルエラーも確認できます。

## 後ろにブロックを置いても1つの式

OSV語順は、引数と関数名の順序だけにとどまりません。
高階関数では、動詞の後ろに処理のスコープを開けます。

```text
fun main: () -> () = {
    with Arena { } {
        val values = [1, 2, 3]

        values map {
            it + 1
        } filter {
            it > 2
        } |> list_count |> println
    }
}
```

`values map { ... }`は、`values`を目的語、`map`を動詞、その後ろのブロックを`map`が開くスコープとして読みます。
ブロック内の`it`は、対象の要素を指す文脈上の束縛です。

`map`の式全体が新しい値になり、その値を次の`filter`が受け取ります。
後ろにブロックがあっても、プログラム全体は値から処理へ向かう順序を保ちます。

明示的に名前を付けたい場合は、ラムダと同じ形で書けます。

```text
values map { |value|
    value + 1
}
```

見た目はKotlinなどのtrailing lambdaに近いですが、Restrictでは「最後の引数だけを後ろへ移動する」という一般規則にはしていません。
最後の引数が関数型の場合に、その引数へ渡す関数の本体を、呼び出し名の後ろへブロックとして書けます。
Restrictでは、この形を式単位のOSV構文として扱います。

## スコープに型を付けて、参照できる値を限定する

Restrictでは、スコープそのものも言語設計の中心に置いています。

`context`で環境の型を宣言し、`with`でその環境をブロックの内側だけに渡せます。

```text
context Logging {
    level: Int32
}

context RequestScope {
    request_id: Int32
}

fun main: () -> Int32 = {
    with Logging { level: 10 } {
        with RequestScope { request_id: 32 } {
            request_id + level
        }
    }
}
```

`level`と`request_id`はグローバル変数でも、レシーバーオブジェクトのプロパティでもありません。
それぞれの`with`が作る字句スコープの内側だけで利用でき、フィールド名と型はコンパイラが検査します。

内側のスコープは、外側の束縛も参照できます。
ブロックの外では、どちらの束縛も存在しません。
設定・ポリシー・リクエスト情報などを暗黙のシングルトンに置かず、型の付いた局所的なスコープで扱えます。

組み込みの`Arena`コンテキストも、同じ`with`の形を使います。
`Arena`が作るアリーナ内で確保したヒープ上の値は、スコープの外へ逃がせません。
集計した整数などのスカラー値は、外へ返せます。

## 所有権を式の中で見えるようにする

Restrictの束縛には、affine ownership（アフィン所有権）の規則があります。
型が`Copy`である場合と、明示的に可変と宣言した場合は、この制限を受けません。
それ以外の値は、0回か1回だけ使用できます。

これは、すべてのコードに所有権のための記号を増やすことが目的ではありません。
ヒープ上の値をどこかへ渡した後、同じ値を誤ってもう一度使う、といった暗黙の複製をコンパイル時に見つけるための規則です。
小さなスカラー値は再利用でき、文字列、リスト、レコードなどは基本的に移動します。

RestrictはトレーシングGCを前提にせず、アリーナを使ってWebAssembly上のメモリを管理します。
型検査では、値の使用回数を数えます。
あわせて、明示的なアリーナの外へ値が漏れていないかを確かめます。

一方で、ライフタイム同士の関係や、より細かなリソース管理のモデルはまだ実験段階です。
v0.0.1では、現在安定して検査できる範囲と将来の構想を分けています。

## 抽象化はコンパイル時に解決する

Restrictにはジェネリクスと、`form`という静的な振る舞いの制約があります。
`form`は実行時に生成するオブジェクトではありません。
必要な関数を具体的な型が実装しているかどうかを、コンパイル時に確認する仕組みです。

標準出力の`print`と`println`も、値の型に対応する`Display`の実装を静的に選びます。
動的なインターフェースオブジェクトやvtableを使わず、選択した実装を特殊化してWebAssemblyを生成します。

型推論は、リテラル・関数の引数と戻り値・周囲の式・ジェネリック関数の利用箇所から、型の制約を集めます。
推論の手がかりが足りない場合は、既定の型を当てはめず、型注釈を求めるエラーを出します。

## v0.0.1でできること

現在のRestrictには、次の機能があります。

- OSV語順の関数呼び出しとパイプライン
- 型付きcontextと`with`スコープ
- アフィン所有権とアリーナによるメモリ管理
- 双方向型推論・ジェネリクス・静的な`form`
- レコード・列挙型・パターンマッチ・`Option`・`Result`
- ラムダと`map`・`filter`・`fold`などのコレクション変換
- WebAssemblyコンパイラとブラウザPlayground
- プロジェクト管理ツールWarderとLSP

ソースコードからプロジェクトを作成し、チェック、ビルド、実行、テストするところまで一通り試せます。
ブラウザPlaygroundではインストールせずに、同じ言語機能の一部を確認できます。

## まだできないこと

v0.0.1は最初の公開版であり、完成した言語ではありません。

| HomebrewやVS Code Marketplaceからの安定した配布 | 未整備 |
| 複合型やジェネリック型をホストと受け渡すWebAssembly ABI | 設計中 |

できることだけでなく、まだ保証していない範囲も明示します。

## なぜ今公開するのか

言語処理系は、構文を増やし続けるだけでは、いつまでも公開できません。
どこまでを現在の言語として保証し、何を実験として残すのかを決める必要があります。

v0.0.1を、Restrictの最初の基準にしました。
コンパイラ・言語仕様・ドキュメント・Playground・CLIを同じタグにそろえ、これ以降の変更をv0.0.1との違いとして説明できるようにしています。

OSV語順が読みやすいのか。
型付きスコープで参照できる値を限定する設計が役立つのか。
アフィン所有権とWebAssemblyの組み合わせに、どのような使い道があるのか。

まだ答えが固まっていない部分もあります。
今後は実際に触った読者から、フィードバックを受け取ります。
